# Среда claude-box (@PROFILE_RU@)

Ты работаешь в изолированном Docker-контейнере `@PREFIX@-agent` на машине пользователя (@HOSTNAME_RU@),
а **не на самой машине**. Пользователь `agent`, sudo нет. В начале сессии приходит сводка
«Окружение claude-box»; текущее состояние в любой момент показывает команда `box-info`.
Если не понимаешь, где что находится, сначала запусти `box-info` и прочитай этот файл, а не исследуй
систему наугад.

## Карта: что откуда доступно

| Куда | Из контейнера | Как правильно |
|---|---|---|
| Интернет | только через SOCKS5-прокси (TUN) | напрямую: `curl`, `git`, `npm` и т.п. |
| Хост (@HOSTNAME_RU@) | только SSH-алиас `@HOST@` | `ssh @HOST@ '<команда>'`, каждый раз с подтверждением пользователя |
| Другие серверы по SSH | через прокси | `ssh <алиас> '…'`, тоже с подтверждением |
| Локальная сеть хоста | **недоступна** | через хост: `ssh @HOST@ 'curl …'`, `ssh @HOST@ 'ssh … "…"'` |
| Рабочие файлы | `/workspace` | это же папка на хосте (`box-info` покажет путь) |

## Сеть: важные особенности
- Весь трафик контейнера идёт через туннель в SOCKS5-прокси, прямого выхода нет. Kill-switch пропускает
  наружу только соединение с прокси (и SSH на хост). Не пытайся менять сеть, DNS или маршруты: это сломает
  работу, но защиту не обойдёт.
- **Частные адреса** (`192.168.*`, `10.*`, `172.16–31.*`, `169.254.*`, `100.64–127.*`) из контейнера закрыты.
  Хук остановит такие команды и подскажет путь через хост. Исключение — подсети, которые пользователь сам
  открыл в `DIRECT_CIDRS` (их покажет `box-info`); обращения к ним тоже подтверждает пользователь.
- **Ложно открытые порты.** TUN принимает TCP-подключение к любому адресу и порту ещё до того, как
  выяснится, что ехать некуда. Поэтому `nc -z`, `telnet`, `nmap`, `/dev/tcp` отсюда всегда «видят» открытый
  порт. Доступность чего-либо в локальной сети проверяй только с хоста: `ssh @HOST@ 'nc -z -w 3 <ip> <порт>'`.
- Имена вроде `my.keenetic.net`, `router.asus.com`, `*.local` знает только DNS локальной сети. Из контейнера
  DNS идёт через прокси в DoH, поэтому используй IP-адрес и работай через хост.
- Часовой пояс и локаль контейнера выставлены по стране прокси. Это сделано намеренно, не меняй их.

## SSH и действия за пределами контейнера
- Любая SSH-команда (`ssh`, `scp`, `rsync … host:`, `sftp`) — это действие за пределами контейнера.
  Каждая требует подтверждения пользователя.
  - Перед запросом коротко объясни, что команда сделает.
  - Объединяй однотипные действия в одну команду, чтобы не заваливать пользователя запросами.
- Не упаковывай такие команды в скрипты, tmux-окна или другие обёртки, чтобы пользователь видел каждую
  команду. Хук подтверждения всё равно сработает и на такие варианты.
- Пароли **не подбирай и пароли по умолчанию не пробуй**. Нужен доступ — спроси пользователя. Лучше всего
  вход по SSH-ключу. Если вход только по паролю, пусть пользователь выполнит интерактивную часть сам
  (подготовь ему точные команды) или настроит ключ.

## Интерактивные программы
- Инструмент Bash не интерактивный: команды, которые ждут ввода (пароль, меню, `y/n`), зависнут.
  Ищи неинтерактивный вариант (флаги `-y`, `--yes`, ввод через stdin или heredoc, файл ответов).
- Долгие процессы внутри контейнера (dev-сервер, сборка) запускай в отдельном окне tmux и читай его вывод
  через `tmux capture-pane -p -t <окно>`. Ввод в окно с SSH-сессией (`tmux send-keys`) требует подтверждения.
- Интерактивный сценарий на хосте или другом устройстве (мастер настройки, меню) лучше отдать пользователю:
  дай ему готовую команду и попроси прислать вывод.

## Ограничения и безопасность
- Хуки, правила подтверждения, маски секретов, kill-switch — это защита, которую поставил пользователь.
  Не исследуй их устройство и не ищи обходов. Если что-то заблокировано, объясни пользователю, что и почему,
  и предложи разрешённый путь (`ssh @HOST@`, действие с его стороны).
- Не выводи секреты (пароли из `.env`, токены, ключи) целиком в ответах.
